System Thinking

Systems Architecture · Chapter 2

Aykut C. Satici

What Is System Thinking?

  • Thinking about a question, circumstance, or problem explicitly as a system
  • Goal: help complex systems appear less complicated
  • Two levels of ambition:
    • Understanding what is — making sense of a system
    • Predicting what might be — if something changes

Tip

At the pinnacle of system thinking is synthesizing a system — the subject of Part 3 of this course.

Define system thinking precisely before doing anything else with it: it is simply thinking about a question, circumstance, or problem explicitly as a system — a set of interrelated entities — rather than thinking about it in some other way. It is deliberately not the same thing as “thinking systematically” (i.e., methodically or step-by-step); the word “system” here refers to the object of thought, not the manner of thinking.

It’s also useful to mention that system thinking sits alongside other modes of reasoning students already use without naming them — critical reasoning (evaluating whether a claim is valid), analytic reasoning (deriving conclusions from a set of laws or principles), and creative thinking. Well-prepared thinkers use all of these modes and are aware of which one they’re using at any moment — a skill sometimes called meta-cognition.

There are two levels of ambition here, and it’s worth being explicit that they are genuinely different in difficulty. Understanding what is — making sense of an existing system — is the more basic goal. Predicting what might be, if something about the system changes, is considerably harder, because it requires anticipating emergent behavior (which we’ll get to shortly). And the callout fragment previews the entire arc of the course: at the very top of the ambition ladder is synthesizing a system from scratch — designing its architecture — which is exactly what Part 3 of this course (Chapters 9–13) is about. Everything in this chapter is building toward being able to do that well later.

Four Tasks of System Thinking

  1. Identify the system, its form, and its function
  2. Identify the entities of the system, their form and function
  3. Identify the relationships among the entities
  4. Identify the emergent properties of the system

These four tasks structure the rest of this chapter.

Preview the chapter’s entire structure in one slide — this is the map students should keep in the back of their minds through everything that follows. Each of these four tasks gets its own dedicated section later in the chapter (Sections 2.3 through 2.6), and each will be applied to the same four running examples: the amplifier circuit, a design team (“Team X”), the human circulatory system, and the solar system.

Emphasize up front — because it will look like a contradiction later if you don’t — that although these four tasks are presented sequentially here for teaching purposes, in real practice system thinking is rarely done in strict sequential order. An experienced practitioner iterates: identifying a relationship might reveal a new entity you missed, or trying to predict emergence might send you back to reconsider the system boundary. The numbered order is a pedagogical scaffold, not a rigid procedure.

Box 2.1 · Definition: System

A system is a set of entities and their relationships, whose functionality is greater than the sum of the individual entities.

  • Almost anything can be considered a system — almost everything contains entities and relationships
  • What matters is whether treating it as a system is useful
  • The second half of the definition is the important half — it’s what makes a system more than a pile of parts

This is the single most important definition in the chapter, so slow down here. It has two distinct parts, and students should be able to recite both. First: a system is made up of entities that interact or are interrelated — this part alone doesn’t distinguish a system from a random pile. Second, and this is the crucial part: when those entities interact, there appears a function that is greater than, or other than, the functions of the individual entities. That second clause is what makes the definition non-trivial.

It’s worth walking through the book’s own stress-test of this definition: what does not qualify as a system? A brick, at the macroscopic level we usually care about, is not a system — it’s uniform throughout, no distinguishable entities or relationships at that scale. A set of entities with no relationships among them (the book’s example: a person in Ukraine and a bag of rice in Asia, with no connection between them) also isn’t a system. But push on the scale and the answer can flip: zoom into the brick’s microstructure and it is arguably a system (clay particles, sharing load, held in a geometric arrangement); have the person in Ukraine spend a euro buying that Asian rice, and now there’s a relationship linking them into a trading system. The lesson: almost anything can be considered a system, at the right scale — so the interesting question is never “is this technically a system?” but “is treating it as a system useful for the problem at hand?”

Also flag two adjacent words that often get conflated: a product is something that is, or could be, exchanged (some products aren’t systems, like a bag of rice; some systems aren’t products, like the solar system — but many things are both). And architecture, the subject of the whole course, is simply an abstract description of a system’s entities and their relationships — so system and architecture are intimately linked concepts.

Systems and Emergence

A system is a set of entities and their relationships, whose functionality is greater than the sum of the individual entities.

This is emergence — the power and the magic of systems. It’s why we build them.

Isolate the second half of the definition and give it its proper name. This highlighted clause — “whose functionality is greater than the sum of the individual entities” — is what the field calls emergence. Emergence is what appears, materializes, or surfaces only when the system operates as a whole; it cannot be found by looking at any individual entity in isolation. Make sure students understand this isn’t mystical language dressed up as jargon — it’s a precise technical term we’ll use constantly for the rest of the course.

Drive home why this matters practically, not just definitionally: emergence is why we bother building systems at all, rather than just collecting useful individual parts. Nobody wants a pile of sand and a funnel-shaped tube sitting on a shelf — but put them together in the right configuration, and you get something neither one could do alone: an hourglass that keeps time. That’s the “power and the magic” language on the slide, and the next few slides make it concrete with real examples.

What Emerges?

  • Function — what a system does: its actions, outcomes, outputs
    • Anticipated and desirable (cars transport people)
    • Anticipated but undesirable (cars burn hydrocarbons)
    • Unanticipated but desirable (cars provide a sense of freedom)
    • Unanticipated and undesirable (cars can kill people)
  • Performance — how well the system executes its function
  • The “ilities” — reliability, maintainability, safety, robustness — emerge over the system’s lifecycle, not immediately

Break “emergence” down into the different kinds of things that can emerge, since students will otherwise think of it only as “surprising side effects.” The most obvious thing that emerges is function — a system’s actions, outcomes, or outputs. Function further splits along two independent axes: was it anticipated by the designer or not, and is it desirable or not? That gives four combinations, and cars illustrate every one of them cleanly: transporting people is anticipated and desirable (this is why we build cars — this primary function is usually tightly linked to the benefit that motivates building the system at all); burning hydrocarbons is anticipated but undesirable (engineers know this happens, they just can’t avoid it entirely); giving people a sense of personal freedom is unanticipated but desirable (nobody designed cars to produce this feeling, yet it clearly does, and it’s part of why people buy them); and cars killing people is unanticipated and undesirable — the most serious category, which the next few slides build toward.

Beyond function, performance also emerges — not just “does it do the thing” but “how well does it do the thing.” How quickly does the car transport people? How accurately does the hourglass keep time?

And finally there’s a category the book calls the “ilities” — reliability, maintainability, operability, safety, robustness, and similar properties. The key distinguishing feature of the ilities, worth emphasizing because it’s easy to miss: unlike function and performance, which tend to emerge and create value immediately when the system operates, the ilities typically emerge over the system’s lifecycle — you don’t know how reliable something really is until it’s been running for years. This is a subtlety that will matter later in the course when we discuss architecting for the long haul, not just for day-one performance.

Figure 2.1 · Emergence from Sand and a Funnel

Neither sand nor a funnel-shaped tube has a “timekeeping” function on its own — put together, the emergent function of keeping time appears. Source: Crawley, Cameron & Selva (2016), Fig. 2.1. Photo: LOOK Die Bildagentur der Fotografen GmbH/Alamy.

This is the book’s cleanest, simplest illustration of emergence, and it’s worth dwelling on precisely because it’s so simple. Consider the two elements pictured: sand (a natural material, with no built-in “timekeeping” function whatsoever) and a funnel-shaped glass tube (which just channels or concentrates a flow — also no timekeeping function on its own). Put together, in the right geometric arrangement, a genuinely new function emerges: keeping time. Ask students rhetorically — how could anyone have predicted, just from examining sand and funnel-shaped glass separately, that combining them would produce a device that tracks the passage of the abstraction we call “time”? Nothing about either component in isolation suggests it. That unpredictability from the parts alone is the essence of emergence, and it’s why understanding it is called both “the goal” and “the art” of system thinking — it takes real skill and experience to anticipate what will emerge from a new combination of entities.

Box 2.2 · Principle of Emergence

“A system is not the sum of its parts, but the product of the interactions of those parts.” — Russell Ackoff

“The whole is more than the sum of the parts.” — Aristotle, Metaphysics

  • The interaction of entities leads to emergence
  • As a consequence, change propagates in unpredictable ways
  • It is difficult to predict how a change in one entity will influence emergent properties
  • System success = anticipated properties emerge; system failure = they don’t (or unwanted ones do)

This is the chapter’s first formally named “Principle” — worth pointing out that the book’s principles always follow this same format: quotations that show the idea is ancient and enduring (here, one from Aristotle’s Metaphysics, one from 20th-century systems theorist Russell Ackoff), followed by a prescriptive statement of what the principle tells us to actually do. The Ackoff quote is the sharper of the two for our purposes: not “the sum,” but “the product of the interactions” — emphasizing that emergence comes specifically from how entities interact, not merely from their being collected together.

Walk through the four consequences listed here as a connected chain of reasoning, not four independent facts: emergence arises specifically from entities interacting (not just coexisting); because of that, when you change one entity, the effects propagate through those interactions in ways that are genuinely hard to predict in advance; this is why anticipating exactly how a single component change will ripple through to affect emergent system-level properties is a hard problem in general, not a failure of individual engineers; and finally, this gives us a crisp, testable definition of system success and failure — success is when the anticipated properties actually emerge as designed, and failure is either their absence, or the unwelcome appearance of properties nobody wanted. This last framing — success/failure defined purely in terms of emergence — is one students should be able to apply to any system they analyze for the rest of the course.

Figure 2.2 · Emergent Performance

Every soccer team has the same function — score more than the opponent. Performance is how well the system executes it. The German national team, arguably the world’s highest-performing team in 2014, went on to win the World Cup. Source: Crawley, Cameron & Selva (2016), Fig. 2.2. Photo: wareham.nl (sport)/Alamy.

Use this to distinguish function from performance — a distinction students sometimes blur together. Every soccer team in the world, without exception, shares exactly the same function: work together to score more goals than the opponent. If function were the whole story, every team would be identical. What differs — and what emerges from the specific players, their formal relationships (positions, passing patterns) and functional interactions (how they actually play together) — is performance: how well that shared function is executed. The 2014 German national team pictured here is a nice real example because performance emerged from the team as a whole in a way that couldn’t be attributed to any single star player — it was, arguably, the highest-performing soccer team in the world that year, and it went on to win the World Cup. This is a good moment to ask students: can you list a system whose function is common and simple, but whose performance varies enormously based purely on how the parts are put together? (Restaurants, sports teams, and software codebases doing “the same” task are good prompts if the room is quiet.)

Emergency: When Emergence Goes Wrong

  • The most severe class of emergence: severe, unanticipated, undesirable emergence
  • We call this an emergency — same word root as emergence
  • Cars lose traction and spin. A soccer team implodes on the day of a big match.

Hurricane Katrina bearing down on New Orleans. Source: Crawley, Cameron & Selva (2016), Fig. 2.3. Image courtesy GOES Project Science Office/NASA.

Point out the wordplay here explicitly, because it’s a genuinely useful mnemonic, not just a pun: “emergency” and “emergence” share the same word root, and that’s not a coincidence — an emergency is precisely the most severe class of emergence, specifically the unanticipated and undesirable kind. Give both a human-system and a natural-system example: a car losing traction and spinning out is a mechanical system’s emergency; a soccer team completely imploding — falling apart as a cohesive unit — on the day of an important match is an organizational one. Hurricane Katrina, pictured here bearing down on New Orleans, is presented as a natural-system example of catastrophic emergence — reinforcing that these ideas aren’t limited to human-engineered systems; they apply to any system, built or natural.

Section 2.2 Summary

  • A system is a set of entities and their relationships, whose functionality is greater than the sum of the individual entities
  • Almost anything can be considered a system
  • Emergence occurs when the functionality of the system is greater than the sum of the functionalities of the individual entities
  • Understanding emergence is the goal — and the art — of system thinking
  • Function, performance, and the “ilities” emerge as systems operate; so does their absence — and so, in the worst case, does an emergency

Use this slide as a checkpoint, not just a recap to read aloud — ask students to explain each bullet in their own words before you move on, since everything in the rest of the chapter builds on this foundation. By this point they should be comfortable with: the two-part definition of a system; the idea that almost anything can be treated as a system, but usefulness is what decides whether you should; the precise meaning of emergence; the four things that can emerge (function, performance, the ilities, and — in the worst case — an emergency); and why understanding emergence is described as both the “goal” and the “art” of system thinking — goal because it’s what we’re trying to achieve, art because, as we’ll see, there’s no guaranteed formula for predicting it. From here, the chapter turns from “what is a system and why does it matter” to the concrete four-task procedure for actually doing system thinking.

2.3 Task 1

Identify the System, Its Form, and Function

Task 1: Identify the system, its form, and its function.

  • Form is what the system is — physical or informational, with shape, configuration, arrangement, layout
  • Function is what the system does — the action for which it exists
  • Form is not function, but form is necessary to deliver function

This section-header slide launches the first of the four tasks. Define form and function crisply, since they’re a pair of terms the entire rest of the course depends on. Form is what the system is — it can be physical (a shape, a configuration, an arrangement, a layout) or purely informational, and importantly, form is relatively static and perseverant over some period of time, even though it can be created, altered, or destroyed. Function is what the system does — the actions, operations, or transformations it performs, the reason it exists or is employed.

The relationship between them is the key idea to land here, and it’s subtle enough that it’s worth stating twice, in two different ways: form is not function — you cannot reduce “what a thing does” to “what a thing is” — but form is necessary to deliver function; you can’t have function floating free of some physical or informational embodiment that carries it out. This sets up the whole first task: for any system we care about, we need to be able to name both what it is (form) and what it does (function), and see how the latter depends on, but is not identical to, the former.

Four Running Examples

We’ll use these four systems throughout the rest of the course — chosen to span built and evolved, informational, organizational, mechanical, and natural systems.

Amplifier circuit
Design team (Team X)
Circulatory system

Source: Crawley, Cameron & Selva (2016), Figs. 2.4–2.7.

Introduce these four examples as a set students should get comfortable with, because we’ll return to all four repeatedly for the rest of the chapter (and Team X specifically returns, extended, in Chapter 3). The selection is deliberate, not arbitrary — point out the diversity: the amplifier circuit is a simple built electronic system; the design team (Team X — three people whose job is to develop a device design) is an organizational system; the circulatory system is a natural, evolved biological system; and the solar system is a natural, physical system with no designer at all. Spanning built, evolved, informational, organizational, mechanical, and natural systems from the very start makes the point implicitly that system thinking isn’t a technique specific to engineering — it applies uniformly across all of these very different domains. Keeping the examples this simple (2–3 entities each) is also deliberate: it lets us fully master each of the four tasks before Chapter 3 scales everything up to genuinely complex systems.

Function = Process + Operand

  • The process is the pure action or transformation — the part that changes the state of something
  • The operand is the thing whose state is changed — created, destroyed, or altered
  • In organizations, function is sometimes called role or responsibility

Tip

For the amplifier: the process amplifies, and the operand is the output signal.

Decompose “function” one level further, since “what a system does” is still too coarse a concept to work with formally. Every function has two parts: a process, which is the pure action or transformation itself — the part that actually changes something’s state — and an operand, which is the thing whose state gets changed (created, destroyed, or altered in some way). Function is inherently transient in this sense: it’s always about a transition happening to some operand, not a static property.

Give the amplifier circuit as the running worked example, since it’s the cleanest of the four: the process is “amplifies,” and the operand is the “output signal” — the process takes an operand (broadly, the signal) and changes its state (amplifies its magnitude). Note in passing, since it’ll come up again with Team X, that in organizational contexts function is often expressed using the words “role” or “responsibility” instead — same underlying concept, different vocabulary depending on the domain.

The solar system’s function is especially emergent — it requires both a constant solar output and a roughly constant planetary orbital radius.

Walk across all four running examples in one table, applying the process/operand decomposition uniformly. The amplifier’s form is the circuit itself, its process is “amplifies,” its operand is the output signal. Team X’s form is the team (the collective of individuals), its process is “develops,” its operand is the design. The circulatory system’s form is, well, the circulatory system, its process is “supplies,” its operand is oxygen (to the body’s cells). The solar system’s form is the solar system itself, its process is “maintains,” and its operand is a constant solar energy flux to the planets.

Spend extra time on the solar system row, because it’s the most conceptually interesting and the fragment calls it out for a reason: its function is especially emergent. To maintain a genuinely constant flux of solar energy reaching a planet, you need two independent things to hold steady together — a constant solar energy output from the sun, and a roughly constant orbital radius for the planet. Neither the sun’s output alone nor the orbital mechanics alone produces “constant flux” — it’s the combination, the emergent product of both, that does. It’s also worth noting how much harder it is to state the solar system’s function than the other three: for anything a person designs and builds (the amplifier, the team), you could, in principle, just ask the designer what they intended. For natural or evolved systems, there’s no designer to ask, and there could be dozens of equally valid ways to state the function — an Earth-centric formulation (“maintains Earth’s temperature to support life”) is just as defensible as the more general one used here.

Instrument – Process – Operand

  • Every system has an instrument of form (what it is) and a function, which breaks into a process (the transformation) and an operand (what’s transformed)
  • Noam Chomsky’s transformational grammar: every sentence has a noun (instrument), a verb (process), and a noun (operand)

noun – verb – noun
= form – process – operand

This instrument–process–operand pattern may be fundamental to how the human brain understands any system.

This slide makes an intellectually striking claim, worth giving room to breathe rather than rushing past. Every system we’ve looked at so far decomposes cleanly into the same three-part pattern: an instrument of form (what the thing is), a process (the transformation it performs), and an operand (what gets transformed). The book draws a deliberate parallel to linguistics: when Noam Chomsky developed transformational grammar, he found that the deep structure underlying all human language consists of exactly three parts — a noun that’s the instrument of the action (our “form”), a verb describing the action (our “process”), and a second noun that’s the object of the action (our “operand”). Every basic sentence in every human language has this noun–verb–noun structure.

The fragment states the implication plainly: this pattern might be either fundamental to how systems actually work, or fundamental to how the human brain is wired to understand systems — and honestly, either way, it’s extremely useful. It’s a good moment to have students try it themselves: pick any system, state its function as a single sentence, and check whether it naturally falls into noun–verb–noun (instrument–process–operand) form. If it’s awkward to state that way, that’s often a signal the “system” or its function hasn’t been well identified yet.

2.4 Task 2

Identify the Entities

Task 2: Identify the entities of the system, their form and function, and the system boundary and context.

  • Systems are composed of a set of entities — their constituents
  • Each entity also has its own form and function
  • Selecting entities is guided by holistic thinking and by focus

Move to the second task. Having identified the system as a whole (Task 1), we now open it up: systems, by definition, are composed of a set of entities — their constituent parts. The recursive idea here is important and worth stating explicitly: each of these entities also has its own form and its own function, exactly the same way the whole system did in Task 1. This is the first hint of a theme (recursion) that gets its own formal name in Chapter 3.

Flag up front that selecting which entities to consider is not mechanical — it’s guided by two techniques the rest of this section develops in detail: holistic thinking (casting a wide net to make sure nothing important is missed) and focus (narrowing that wide net down to a manageable, consequential set). Both get their own principle and their own worked example on Team X in the slides that follow.

Table 2.3 · Entities Have Form and Function Too

System Function Entity Function Entity Form
Amplifies signal Sets gain Resistor 1, Resistor 2
Amplifies voltage Operational amplifier
Supplies oxygen Pumps blood Heart
Exchanges gasses w/ atmosphere Lungs
Exchanges gasses w/ organs Capillaries

Reading right to left — combining entities into the system — is aggregation. Reading left to right — breaking the system into entities — is decomposition. Doing the same with function is called zooming, and reversing it recovers emergence.

Walk through the amplifier and circulatory-system rows concretely: the amplifier circuit’s overall function (“amplifies signal”) decomposes into the entity functions “sets gain” (delivered by the form of two resistors) and “amplifies voltage” (delivered by the operational amplifier’s form). Similarly, “supplies oxygen” as a system function decomposes into three entity functions — the heart pumping blood, the lungs exchanging gases with the atmosphere, and the capillaries exchanging gases with organs — each with its own corresponding entity form.

The fragment introduces four important pieces of vocabulary at once, so take it slowly and make sure the directionality sticks, since students often confuse these terms later. Reading the table right-to-left in the form columns — combining individual entities of form into the system’s form — is called aggregation. Reading left-to-right in those same columns — breaking the system’s form into constituent entities — is decomposition. Now shift to the function columns: reading left-to-right there — breaking system function into more granular entity functions — is called zooming. And reversing that direction — recombining entity functions back up into system-level function — is exactly how we recover emergence (since, recall, emergence is precisely “more than the sum,” so combining entity functions back up is where the interesting, non-additive behavior shows up). It’s worth pointing out explicitly that decomposition/aggregation is the form-domain pair, and zooming/emergence is the function-domain pair — the same basic idea of “breaking apart vs. building up,” applied separately to each domain.

Five Issues for the Systems Thinker

  1. Defining the initial decomposition into entities
  2. Identifying potential entities using holistic thinking
  3. Winnowing down to consequential entities using focus
  4. Creating abstractions for the entities
  5. Defining the boundary of the system, separating it from context

Give students the roadmap for the rest of this section — these five issues are addressed one by one over the next several slides, using Team X as the running worked example throughout, so it helps to have them all listed up front. First, how do you even begin dividing the system into entities? Second, how do you make sure you’ve considered everything potentially relevant (holistic thinking)? Third, given that holistic thinking usually surfaces far too much, how do you narrow back down to what actually matters (focus)? Fourth, once you’ve settled on a set of entities, how do you represent each one usefully, hiding irrelevant detail (abstraction)? And fifth, where exactly do you draw the line between “in the system” and “outside the system, but still relevant” (the boundary and context)? Each of the next slides tackles one of these in turn.

Modular vs. Integral Systems

Modular

  • Made of clearly distinct entities
  • Internal relationships are dense within a module, weak between modules
  • Decomposition is challenging but relatively clear

Integral

  • Highly interconnected — hardest to decompose
  • Cannot be easily divided without breaking function
  • Example: a car’s steering mechanism (tires, wheels, suspension, column — all simultaneously part of other systems too)

Some systems are trivially distinct (Team X: three separate people) — decomposition there is obvious.

This is issue #1 from the previous slide — defining the initial decomposition — and the book frames the difficulty as a spectrum with three named points along it. At one end, systems made of trivially distinct elements: Team X, three separate people, is the book’s own example, and there’s really no meaningful alternative decomposition — of course the entities are the three people. At the other extreme, integral systems are highly interconnected and genuinely hard to decompose without breaking their function — the book’s example is a car’s steering mechanism: the tires, wheels, suspension, and steering column are so tightly interwoven functionally that you can’t cleanly separate them, and to make it worse, several of those same components are simultaneously part of other systems too (the suspension is part of the ride-quality system, for instance). Complex forgings, machined parts, and integrated circuits are other examples of genuinely integral systems.

In between sit modular systems: made of clearly distinct entities, where relationships are dense within a module but comparatively weak between modules. Decomposition of a modular system is still real work — it’s “challenging but relatively clear” — but nowhere near as hard as an integral system. The amplifier circuit sits here: there’s some fuzziness about exactly where a resistor ends and its connecting wire begins, but broadly the entities (resistors, amplifier, connections) are clear. This spectrum — trivially distinct, modular, integral — is worth having students practice classifying: ask them where their own course project’s system falls on it.

Box 2.5 · Principle of Holism

“Always design a thing by considering it in its next larger context — a chair in a room, a room in a house, a house in an environment, an environment in a city plan.” — Eliel Saarinen

“No man is an island, entire of itself…” — John Donne

  • To think holistically is to encompass all aspects of the system at hand — influences, consequences, anything that might interact with it
  • Methods: structured/unstructured brainstorming, frameworks, thinking from different perspectives, thinking about context

This is issue #2 — identifying potential entities via holistic thinking — now formalized as a named principle. Unpack both quotes, since they emphasize slightly different aspects: the Saarinen quote is specifically about nested context — a chair belongs in a room, which belongs in a house, which belongs in an environment, which belongs in a city plan, each layer providing context for the one below it. The Donne quote is more about interconnection generally — nothing exists in true isolation from everything around it.

Define holism precisely, since it’s easy to state vaguely: to think holistically is to encompass all aspects of the system at hand, taking into account every influence and consequence, anything that might conceivably interact with the system — it’s explicitly the opposite of reductionism, which instead tries to understand a whole by carefully explaining only its parts. Give students the concrete methods listed for actually doing holistic thinking, since “just think about everything” isn’t actionable advice on its own: structured and unstructured brainstorming (we’ll return to this with real technique in Chapter 11 on stakeholders), building frameworks or checklists to make sure relevant categories of issue are covered (a running theme of Chapters 4 through 8), deliberately thinking from multiple different perspectives, and explicitly thinking about context. The Team X walkthrough on the next slide shows holistic thinking actually being applied, not just described.

Known-Unknowns vs. Unknown-Unknowns

Known-unknown

Something you know is there, but don’t know much about. Its presence is known; its features aren’t.

Unknown-unknown

Something you don’t even know is there — no way to evaluate its importance until it surfaces.

Tip

Holistic thinking works to convert as many unknown-unknowns into known-unknowns as possible.

Give students the precise vocabulary for why holistic thinking matters, not just that it does. A known-unknown is something whose presence you’re aware of, even if you don’t yet know much about its details or features — you know there’s a gap in your knowledge, and you can go fill it if needed. An unknown-unknown is far more dangerous: something you don’t even know exists, so you have no way to evaluate its importance, budget time to investigate it, or plan around it — it simply isn’t on your radar at all, until (often unpleasantly) it surfaces on its own.

The fragment states holistic thinking’s real payoff crisply: its job is to convert as many unknown-unknowns into known-unknowns as possible. It can’t eliminate uncertainty — you still won’t know everything about every entity — but it can at least get everything relevant onto the table, as a known gap rather than a blind spot. This is a good moment to connect back to the John Deere crop-sprayer example from Chapter 1: the column-separation constraint at the manufacturing site was an unknown-unknown to whoever set up the naive productivity equation, and it should have been surfaced as at least a known-unknown through more holistic thinking about the system’s full context.

Box 2.6 · Principle of Focus

“I see no more than you, but I have trained myself to notice what I see.” — Sherlock Holmes (Arthur Conan Doyle)

“The question is not what you look at but what you see.” — Henry David Thoreau

  • Holistic thinking can surface tens or hundreds of potentially relevant entities — too many for any team to hold at once
  • The human brain can reason about roughly seven ± two things at a time [Miller, 1956]
  • Failure rarely occurs in aspects on which you focus — it hides in what you left out

This is issue #3 — winnowing down using focus — and it directly answers the problem the previous two slides created: holistic thinking is supposed to surface tens or even hundreds of potentially relevant entities, but no individual or small team can simultaneously reason about that many things at once. Both quotes point at the same idea from different angles: Holmes and Thoreau are both saying that the raw sensory or informational input available to everyone is roughly the same — the skill is in training yourself to notice and prioritize the right subset of it.

The number “seven plus or minus two” is a real, citable result, not folk wisdom — it comes from George Miller’s classic 1956 paper “The Magical Number Seven, Plus or Minus Two,” on the limits of human short-term information processing, and it recurs constantly throughout this course (we’ll see it again with hierarchy and decomposition sizing in Chapter 3, and again in later chapters). The practical process is: use holistic thinking to generate the long list, then use focus to identify the critical, most consequential items and actively narrow down to something close to that seven-plus-or-minus-two range for the problem at hand.

The last bullet is worth pausing on and repeating verbatim, because it’s a sharp, almost counter-intuitive insight: failure rarely occurs in the aspects you’re actively focusing on — precisely because you’re paying close attention to them. Failure hides in whatever you decided, consciously or not, to leave out of your focus. This reframes “focus” from a purely positive act (choosing what to look at) into also a risk decision (implicitly choosing what not to look at) — and it’s a nice callback to why holistic thinking has to come first, to make sure the things being excluded by focus are being excluded deliberately rather than by accident.

Walk through this table one fragment at a time, live, as a worked example — it’s the single clearest demonstration in the chapter of holistic thinking, focus, and abstraction operating in sequence on a concrete case. Initially, if you asked “who’s on this team,” a narrow view might give you just two people: John, who develops the concept, and Sue, who evaluates and approves the design.

Apply holistic thinking, and the list balloons: suddenly Amy (interpreting requirements), Heather (customer needs), Chris (competitive analysis), Karen (manufacturing planning), James (supply chain), Nicole (regulatory interpretation), Meagan (team coaching), and even John himself wearing a second hat (modeling project finance) all surface as potentially relevant. That’s now nine entities — more than the seven-plus-or-minus-two an individual can comfortably reason about at once.

Apply focus, and the list narrows back down: the team decides finance, team dynamics, and regulation aren’t consequential for the question at hand right now, and drops Meagan, Nicole, and John’s finance-modeling role from active consideration, keeping Amy, Heather, Chris, Karen, and James alongside John and Sue.

Finally, apply abstraction (the next issue on our list, covered properly on the next slide): Heather and Chris — both handling market-facing concerns — get combined into a single abstraction called “Marketing,” and Karen and James — both handling production-facing concerns — become “Operations.” This is a good moment to point out that this four-stage evolution — initial view, holistic expansion, focus narrowing, abstraction compression — is a repeatable pattern students can apply to any system-thinking exercise of their own.

Creating Abstractions

An abstraction brings important details to the surface and hides the rest.

  • Op-amp → “amplifies the difference between two inputs”
  • A person → a “team member” who creates concepts
  • The heart → a simple pump
  • Planet Earth → a sphere

The detail hidden inside the “op-amp” abstraction. Source: Crawley, Cameron & Selva (2016), Fig. 2.8.

This is issue #4 — abstraction — and it’s worth defining precisely since it will get its own set of guidelines on the next slide. An abstraction is “expression of quality apart from the object,” or equivalently, a representation “having only the intrinsic nature [of the thing] rather than the detail.” In plain terms: an abstraction brings the important details to the surface and hides everything else you don’t need for the problem at hand.

Every example on this slide is doing exactly the same job at wildly different scales of underlying complexity. We abstract the operational amplifier — an extraordinarily complicated real circuit, shown fully in the figure with dozens of internal transistors and resistors — into just “a device with an inverting input, a non-inverting input, and an output, that amplifies the difference between the inputs.” All that internal transistor-level detail is hidden; only the input/output behavior we care about is surfaced. Similarly, we abstract a physiologically and psychologically enormously complex human being into simply “a team member who creates concepts” for the purposes of the Team X analysis. We abstract the heart — a genuinely intricate organ with four chambers, valves, electrical conduction — into “a simple pump.” And we abstract the entire solid mass, ecosystem, and population of planet Earth into just “a sphere,” when that’s all the solar-system-scale analysis actually requires. In every case, notice the same move: enormous hidden complexity, replaced by a simple surface representation adequate to the question being asked.

Guidelines for Good Abstractions

  • Represent the important information on the surface, concealing less important detail
  • Allow for representation of appropriate relationships
  • Create abstractions at the right level of decomposition or aggregation
  • Create the minimum number of abstractions that effectively represent the system

Abstractions aren’t unique — which one is “right” depends on the question at hand.

Generalize the previous slide’s examples into four actionable guidelines students can apply when building their own abstractions. First: surface the important information, conceal the rest — this is the core definition restated as an instruction. Second: make sure the abstraction still allows the relationships you actually need to represent (an abstraction that hides so much detail it can no longer connect to anything useful is a bad abstraction, even if it’s simple). Third: pick the right level of decomposition or aggregation for the question — too fine-grained wastes effort on irrelevant detail, too coarse loses something you needed. Fourth: use the minimum number of distinct abstractions that still effectively represents the system — this is a parsimony principle, resisting the temptation to keep proliferating slightly-different abstractions when fewer would do.

It’s worth giving students a concrete example of a bad abstraction to sharpen the guidelines, since the book does this explicitly: abstracting an operational amplifier as simply “a heat source” would be technically true (it does dissipate some heat) but violates the first guideline, since it fails to surface the amplifier’s important role in amplification. Conversely, representing every internal transistor of the op-amp (as shown in the earlier figure) violates the third and fourth guidelines by including far more detail than needed for most circuit-level reasoning.

The closing fragment is an important epistemological point, not just a caveat: abstractions are not unique. There isn’t one single “correct” abstraction of the heart or of a team member — which abstraction is right depends entirely on the question, circumstance, or problem currently at hand. This should reassure students that there’s no single correct answer key to memorize; the skill is in choosing an abstraction well-suited to the task in front of you.

Context is what surrounds the system — entities “just outside” that are still relevant to it.

Amy interprets requirements

Solid boxes = in the system  ·  faded boxes = context (outside the boundary)

When a relationship crosses the boundary, it defines an external interface.

This is issue #5, the last on our list — drawing the system boundary — completing Task 2. Define context precisely: it’s what surrounds the system, the entities that sit “just outside” it but remain relevant. All systems (short of the entire cosmos) have boundaries; we always define a limited extent, either because we’re simply incapable of considering something more extensive (a human-capability limitation), or because we judge it’s not useful to go further (a deliberate human judgment call).

The diagram makes the Team X boundary concrete, continuing directly from the Table 2.4 example: after applying holistic thinking, focus, and abstraction, we’re left with Amy, John, and Sue inside the system boundary (solid boxes) — because the job we’ve decided the system does is “produce a design” — while the abstracted Marketing and Operations functions sit just outside, in the context (faded boxes), because they support the design process but aren’t part of making the design itself.

The fragment introduces a term that becomes central for the rest of the course: whenever a relationship crosses that boundary line — connecting something inside the system to something in its context — that’s called an external interface. Point out how practically important this concept is going forward: nearly every system of any real complexity has external interfaces (it’s nearly impossible to define a system with none at all, since everything connects to something beyond its boundary), and much of systems engineering discipline, and much of this course later on, is specifically about managing those external interfaces well.

2.5 Task 3

Identify the Relationships

Task 3: Identify the relationships among the entities in the system and at the boundary, as well as their form and function.

Relationships come in two flavors:

  • Formal relationships — exist or could exist stably (a connection, a geometric relationship). Also called structure.
  • Functional relationships — entities doing something to/with each other (operations, transfers, exchanges). Also called interactions.

Move to Task 3, having identified the system (Task 1) and its entities (Task 2) — now we connect them. Remind students of the definition of a system from the start of the chapter: a set of entities and their relationships. We’ve handled the entities; now it’s time to handle the relationships properly.

The two-way split here mirrors the form/function distinction from Task 1, and that parallel is worth making explicit. Formal relationships are ones that exist, or could exist, stably over some period of time — a physical connection, a geometric arrangement — and the adjective “formal” is derived directly from “form,” not from any sense of formality or ceremony; this is sometimes a point of confusion worth heading off directly. We also call formal relationships structure, emphasizing their static, standing nature. Functional relationships, by contrast, are about entities actively doing something to or with each other — operations, transfers, exchanges of something between entities — and we also call these interactions, emphasizing their dynamic, active nature. Both types of relationships can occur purely within the system, or can cross the system boundary (in which case, per the previous slide, they’re external interfaces).

Formal Enables Functional

  • A functional relationship usually requires a formal relationship as its instrument
  • The heart cannot exchange blood with the lung without a connection
  • Team members cannot share results without proximity or an information link
  • Because emergence occurs in the functional domain, functional interactions are ultimately what matter most — but formal relationships are where you start looking
Resistor 1
sets gain
↔
Op Amp

Establish the important dependency between formal and functional relationships, echoing exactly the same pattern from Task 1’s “form is necessary to deliver function.” A functional relationship — entities actively doing something to or with each other — generally requires a formal relationship to serve as its instrument. The heart physically cannot exchange blood with the lung unless there’s an actual connection between them; team members cannot share results with each other unless they have either physical proximity or some information link (email, a shared document, a phone line) connecting them.

The diagram makes this concrete for the amplifier circuit’s Resistor 1 and Op Amp: there’s a formal relationship (they’re physically connected — the thin arrow) that serves as the instrument enabling a functional relationship (current actually flows and is exchanged between them — the thick arrow). It’s genuinely useful to point out to students that in a standard electrical schematic, you’d typically draw just one line between these two components, implying both the connection and the current flow simultaneously — but conceptually, for system-thinking purposes, they’re two logically distinct relationships worth separating.

The last bullet resolves an implicit tension students might be feeling: if functional relationships are what ultimately matter (since emergence, the whole point of the chapter, happens in the functional domain), why did we spend so much time on formal relationships at all? The answer given here is practical, not theoretical: formal relationships tend to be more concrete and easier to observe, so they’re a good starting point for investigation — but the functional relationships they enable are what you should be trying to understand for real system-level insight.

Two Ways to Represent Relationships

Relationship diagram

Boxes for entities, arrows for relationships. Easy to visualize; gets cluttered fast as entities multiply.

N-Squared table

An N×N grid of entities against themselves; off-diagonal cells describe the relationship. More detail, no visual clutter, but less intuitive at a glance.

Tip

Both diagrams distinguish relationships within the system from relationships that cross the system boundary — the external interfaces.

Introduce the two standard representational tools students will see used throughout the rest of the course whenever relationships need to be shown — these appear again and again in later chapters, especially once we get to complex systems in Chapter 3 and DSM-based methods much later. The relationship diagram is the intuitive one: boxes for entities, arrows for relationships, easy to read at a glance for a small system, but it gets visually cluttered fast as the number of entities and relationships grows (we’ll see this exact problem motivate a switch to N-Squared tables for larger systems in Chapter 3).

The N-Squared table trades visual intuition for completeness: it’s an N-by-N grid with the system’s entities listed along both the rows and the columns, and each off-diagonal cell describes whatever relationship exists between that row’s entity and that column’s entity. It never gets visually cluttered no matter how many entities there are (it just gets bigger), but it’s less immediately intuitive to scan than a diagram — you have to actually read cells rather than trace arrows.

The fragment makes an important point that applies to both representations equally: both distinguish clearly between relationships that stay entirely within the system and relationships that cross the system boundary (the external interfaces from Task 2). We’ll see both representation types applied concretely to the amplifier circuit over the next two slides.

External Interfaces

  • Formal and functional relationships can exist across the boundary, between entities in the system and entities in its context
  • These are the system’s external interfaces
  • It is nearly impossible to define a system that has no external interfaces — everything connects to something beyond its boundary

Team X’s external interfaces: to Marketing (needs, competitive analysis) and to Operations (manufacturing, supply chain).

Consolidate the external-interface concept, first introduced with the Task 2 boundary diagram, now stated formally as part of Task 3. Both formal and functional relationships can cross the system boundary, linking an entity inside the system to an entity out in the context — and whenever that happens, we call it an external interface.

Emphasize the strong claim in the second bullet, because it has real practical consequences: it is nearly impossible to define any system that has zero external interfaces. Everything connects to something beyond its boundary, one way or another. This means that identifying and managing external interfaces isn’t an edge case some systems happen to have — it’s a near-universal task every systems thinker will face.

Ground this concretely with Team X, continuing the running example: the system boundary we drew placed Amy, John, and Sue inside, with Marketing and Operations abstracted into context, outside. That means Team X necessarily has external interfaces to both — to Marketing (receiving customer needs and competitive analysis) and to Operations (which needs to know about manufacturing and supply-chain implications of the design). Nearly every real project team will have interfaces like these to the rest of the organization, and part of good systems thinking is deliberately identifying and characterizing them rather than letting them go unexamined.

2.6 Task 4

Predicting Emergence

Task 4: Based on the function of the entities and their functional interactions, identify the emergent properties of the system.

Emergence is the magic of a system — but it’s hard to predict a priori what will emerge from combining the functions of a system’s entities.

This is the fourth and final task, and it brings the chapter full circle: we opened by defining emergence as the power and the magic of systems; now, having done the work of Tasks 1 through 3 (identifying the system, its entities, and their relationships), Task 4 asks us to actually predict what emergent properties will result. Be honest with students up front about the difficulty here, since the book is: this is explicitly framed as hard. Knowing the function of every individual entity, and knowing every functional interaction between them, still does not make it easy to say in advance what will emerge from the combination — that’s precisely what makes emergence “the magic” rather than something mechanically computable in general. The next few slides work through why it’s hard (via failure examples) and then what tools we do have available (precedent, experimentation, modeling).

System Failure

Failure happens two ways: the anticipated desirable emergence fails to occur, or undesirable emergence occurs unanticipated.

  • Gridlock: every car does exactly what it’s built to do, every driver follows the rules — yet the anticipated performance (fast travel) fails to materialize
  • Airbus A320, Warsaw: thrust reverser withheld until both landing gear compressed — but one wing was held low in the crosswind, so one gear never triggered it

A320 overrun in Warsaw, Poland — a system failure where every component worked exactly as designed. Source: Crawley, Cameron & Selva (2016), Fig. 2.12. Photo: STR News/Reuters.

Give students two concrete failure examples that both illustrate the same crucial, somewhat unsettling point: system failure does not require any individual component to malfunction.

Gridlock on a busy roadway is the first example, and it’s deliberately mundane: every car is doing exactly what it’s built to do (transporting its occupants); every driver is following the rules of the road, staying safely in their lane behind the car in front. Every component of the system is functioning perfectly, individually — and yet the anticipated, desired system-level performance (people traveling quickly) completely fails to materialize. This is the “anticipated emergence fails to occur” failure mode.

The Airbus A320 example at Warsaw is the second, more dramatic case, and it’s worth walking through the mechanism in detail because it’s genuinely instructive engineering history: the aircraft’s software was designed, as a safety measure, to withhold deployment of the engine-based thrust reverser until the plane had definitively “landed” — signaled by weight being detected on both main landing gear assemblies simultaneously. On this particular landing, in a strong crosswind, the pilot kept the upwind wing held low as a normal crosswind-landing technique — but this meant one side’s landing gear never fully compressed at touchdown, so the software’s “both gear compressed” condition was never satisfied. The wheel brakes, separately, were ineffective on the wet runway. So when the pilot tried to apply the thrust reverser, the software withheld it exactly as designed, and the aircraft overran the runway. Every single component — the software, the sensors, the brakes, the pilot’s technique — worked precisely as intended, individually. The failure was purely at the system level: an unanticipated, undesirable emergent property arising from how the pieces interacted. This is exactly the “anticipated function fails to occur / unanticipated undesirable function occurs” duality from the top of the slide, and it’s a powerful, sobering illustration of why predicting emergence matters so much in high-stakes engineering.

Three Ways to Predict Emergence

Precedent

We’ve done it before, with minimal changes. Grandfather clocks work like this because grandfather’s did too.

Experiments

Put the entities together and see what happens. Spiral development builds a slice first to check emergence.

Modeling

If function and interaction can be modeled, emergence can sometimes be predicted. Integrated circuits: billions of transistors, modeled with a few lines of algebra.

Without precedent, experiment, or reliable modeling — you are reasoning from judgment alone. This is the crux of system thinking.

Give students the three genuine tools available for predicting emergence, since the previous slide established that this is fundamentally hard — these aren’t guarantees, but they’re the best available levers. Precedent means we’ve built essentially this same combination before, with only minimal changes, so we can reasonably expect similar emergence to result again — the book’s example is charmingly literal: grandfather clocks work the way they do because grandfather’s clock worked that way too; we’re not re-deriving pendulum mechanics from scratch each time.

Experimentation means simply putting the actual entities together and observing what emerges, rather than trying to predict it purely analytically beforehand — this can range from casual tinkering all the way up to highly structured prototyping. Spiral (or iterative) development is the disciplined version of this in a product-development context: build a thin “slice” of the eventual system first, specifically to check what emerges, before committing to building the rest.

Modeling means that if the function of the entities and their functional interactions can be captured mathematically, emergence can sometimes be predicted directly from the model, without needing to build anything physical at all. Integrated circuits are the spectacular success story here: a modern IC might contain billions of individual transistor-level gates, yet its emergent, system-level behavior can be predicted from just a few lines of algebra, given a good enough model of a single transistor and how transistors connect and combine.

The closing fragment is the honest, somewhat sobering bottom line of the whole chapter, worth reading aloud slowly: when a system genuinely has no precedent, cannot be experimented on cheaply, and cannot be reliably modeled, you are reduced to reasoning about what will emerge purely from human judgment. This isn’t a failure of the framework — the book calls this “the crux of system thinking” outright. Genuinely novel product development, especially, routinely lands exactly here, and part of what the rest of this course (particularly Part 3, on creating architecture) is about is sharpening that judgment as much as possible, even when precedent, experiment, and modeling all run out.

Emergence Depends on Structure

The same entities, arranged differently, produce different emergence:

Low-pass filter
Resistor between input/output, capacitor to ground → attenuates high frequencies.
Swap the components → attenuates low frequencies instead.
Mechanical lever
Fulcrum near the far end → magnifies force.
Move the fulcrum closer to the operator → the emergence disappears.
Software segment
IF statement first → conditional execution.
Reorder the sequence → the statement always executes.

Tip

Pattern of connectivity, physical location, and sequence are all formal relationships — and they govern what functionally emerges.

Drive home, with three clean minimal-pair examples, that emergence isn’t just a property of which entities you have — it critically depends on how they’re arranged, i.e., on their formal relationships. This directly reinforces the “Formal Enables Functional” idea from Task 3, but now applied specifically to predicting emergence.

Walk through each pair concretely. The electrical filter: place a resistor between input and output, with a capacitor connecting the output to ground, and you get a low-pass filter — high frequencies are attenuated. Simply swap which component is the resistor and which is the capacitor, using the exact same two parts, and now it’s low frequencies that get attenuated instead — completely different emergent behavior, identical parts, different arrangement (this is the same as Figure 2.13, referenced by the diagram at the bottom of this slide). The mechanical lever: a bar and a fulcrum, with the fulcrum positioned near the far end from the operator, magnifies applied force — move that same fulcrum closer to the operator, and the force-magnification effect disappears entirely, even though it’s the identical bar and identical fulcrum. The software segment: an IF condition placed first in a sequence produces genuinely conditional execution — reorder the exact same two lines of code, and the statement inside now executes unconditionally, every time.

The fragment names the common thread across all three examples: pattern of connectivity (which component connects to which), physical location (where the fulcrum sits), and sequence (what order instructions execute in) are all, at bottom, examples of formal relationships — and this slide’s whole point is that these formal relationships are what govern what functionally emerges. This is a good moment to loop back and ask students to connect this to the “Formal Enables Functional” slide from Task 3 — it’s the same principle, now demonstrated with three vivid minimal pairs rather than stated abstractly.

Section 2.6 Summary

  • Emergence can be predicted a priori via precedent, experimentation, and modeling
  • For unprecedented systems, humans must reason about emergence from judgment
  • Emergence depends on the function of the entities (enabled by form) and on the functional relationships (enabled by formal relationships)
  • It is emergence that gives systems their power — and creates the challenge of understanding and predicting them

Use this as a checkpoint for Task 4 specifically, mirroring the Section 2.2 summary checkpoint earlier in the chapter. By now students should be able to name the three tools for predicting emergence (precedent, experimentation, modeling), acknowledge that genuinely novel systems fall back on human judgment when none of the three apply, and — this is the bullet worth emphasizing most, since it ties Tasks 1 through 4 together into one coherent picture — understand that emergence depends on both the function of the entities (which is enabled by their form, from Task 1/2) and the functional relationships among them (which are enabled by their formal relationships, from Task 3). Nothing about emergence can be understood by looking only at entities in isolation, or only at relationships in isolation — it genuinely requires both. The closing line restates the chapter’s opening theme one more time: emergence is simultaneously what gives systems their power, and what makes them hard to fully understand and predict — that duality is the whole reason system thinking, as a discipline, needs to exist.

This table is the whole chapter compressed into four rows, and it’s worth spending a moment making the parallel structure explicit: each row pairs an essential, defining feature of what a system fundamentally is (left column) with the corresponding task of system thinking that addresses it (right column). Systems have form and function — so Task 1 is to identify exactly that. Systems are composed of entities, each with its own form and function — so Task 2 is to identify those entities, plus the boundary that separates the system from its context. Entities are linked by relationships, both formal and functional — so Task 3 is to identify those relationships. Use this as a genuine study tool, not just a recap: the four tasks aren’t an arbitrary checklist someone invented — each one exists specifically to address one of the four defining features of what a system is. If students can reconstruct this table from memory, unprompted, they’ve genuinely internalized the chapter’s structure.

This diagram closes the loop back to the very first slide of the chapter, which introduced “understanding” and “predicting” as the two levels of ambition of system thinking, with “synthesizing” as the pinnacle. Now we can see the full ladder in one place, and it’s worth walking up it rung by rung. At the base: understanding what is — simply making sense of an existing system, which is what most of this chapter’s four tasks, applied to simple existing systems, have been practicing. One level up: predicting what might be, if something about the system changes — genuinely harder, since it requires anticipating emergence, which we just spent the last several slides establishing is difficult in general.

The next rung up is new to this diagram, and worth calling out explicitly: system thinking’s outputs feed directly into decision making — informing the judgment and balance required to weigh options, identify tensions between competing goals, and decide how a system should react to future change. And at the very top: synthesizing a system from scratch — designing its architecture — which the book explicitly identifies as system architecting, the actual subject of this entire course, and specifically of Part 3 (Chapters 9 through 13). Everything in Chapter 2 has been building the analytical foundation — understanding and predicting — that makes it possible to synthesize well later. Chapter 3, up next, is the last stop before we start scaling these same tools up to genuinely complex systems.
