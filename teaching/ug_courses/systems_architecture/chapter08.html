8.2 Developing the Level 1 Architecture

Expanding Concept to Functional Architecture

  • First task: identify the value pathway — start with the key internal functions from the integrated concept (Question 5b), and link them from inputs/start points to outputs/end points
  • Concept: flying a traveler with an airplane. Primary operand: the traveler. Secondary operand: checked baggage
  • Every process acts on the traveler except purchasing the ticket; the only other operand is the ticket itself — an information object encoding itinerary, status, reservation, and fees
  • Chapter’s first concrete step — picking up exactly where Ch.7 left off: solution-neutral function = transporting a traveler; concept = flying via airplane
  • Task now: expand into functional architecture — first move is identifying the value pathway: chain of key internal functions (Question 5b) linked from inputs to outputs
  • Air travel example (clean, minimal): primary operand = the traveler (state changes all the way through); secondary operand = checked baggage (set aside for now)
  • Elegant observation: every process acts on the traveler except purchasing the ticket, which acts on the ticket — an information object encoding itinerary, status, reservation, fees
  • → Have students predict the diagram before the next slide: traveler progressing step by step (checked-in → … → checked-out), one small side-branch for the ticket

Mapping Function to Form

  • “Zag” back to function: the reservation system is an instrument of virtually every process — the check-in and gate systems only get the traveler checked in and boarded; the flight crew is responsible only for transporting (Question 6a)
  • Non-idealities (6b): this model doesn’t yet handle a transiting passenger, a hub connection, or international travel with passport control
  • Supporting functions (6c) are enumerated in Figure 8.2 but not yet connected — nearly every value-related instrument needs personnel who must be trained and supported (HR), and mapping that fully requires Level 2 detail
  • Zag back to function — map form onto the processes that use it (Question 6a)
  • Pattern revealed: reservation system (holds itinerary, seat, travel-program status) = instrument of virtually every process
  • Contrast: check-in/gate systems = instruments of narrower processes only; flight crew = scoped to transporting alone
  • → This spread (“instrument of almost everything” to “of exactly one”) is itself useful info about where functional load concentrates
  • Non-idealities (6b): book is candid — a transiting passenger, hub connection, or international/passport-control itinerary aren’t handled by this model yet
  • → General lesson: any Level 1 architecture is a simplification; good practice = being clear-eyed about which non-idealities were set aside
  • Supporting functions (6c): the “supporting” ovals in Figs 8.1/8.2 (IT, scheduling, training, HR) are enumerated but not yet wired in
  • → Nearly every value-related instrument involves personnel who need training/HR support — mapping that fully needs detail not visible at Level 1. Exactly the gap Level 2 (next) fills

Sequence and Parallel Threads

  • Sequence (6e) is inferred directly from how Figure 8.2 is drawn: processes are listed vertically in the order they occur
  • Parallel threads (6f) are strongly suggested: baggage has almost an entire parallel path to the passenger, separating at check-in and (hopefully) reuniting at check-out
  • Clock time (6g) clearly matters — aircraft keep real schedules — but that information isn’t shown here; it would need additional diagrams
  • Continue through Ch.6 questions — timing and concurrency
  • Sequence (6e): inferred directly from vertical ordering in the diagram — processes listed top to bottom in experienced order; no extra notation needed
  • Parallel threads (6f): baggage’s near-parallel path pays off here — separates from passenger at check-in, “hopefully” reunites at check-out — strong evidence of real parallel execution, not a single sequential thread
  • → Ask students to name other systems with this same parallel-thread structure
  • Clock time (6g): explicitly not captured — airlines keep real schedules, but nothing shown so far represents this; would need additional timing diagrams
  • → No single diagram type (OPM included) shows everything — different questions call for different representations (echoes Chapter 3’s “views and projections”)

Function-Goal Reasoning

The solution at one level becomes the problem statement at the next.

  • The Level 0 specific function (the functional half of the concept) becomes the functional intent at Level 1
  • That intent is specialized and zoomed into the Level 1 functional architecture — operands and internal processes — while Level 0 form is decomposed into Level 1 entities of form and mapped onto them
  • The rest of Level 1 detail fills in from there: non-idealities, supporting processes and form, interfaces
  • Name and isolate the principle Figure 8.3 illustrated — compact, memorable, invoked repeatedly for the rest of the chapter and again in Section 8.3
  • State exactly: the solution at one level becomes the problem statement at the next. Have students restate it themselves
  • Slightly paradoxical: you’d think “solving” Level 0 means you’re done — instead that solution turns into the question one level down
  • The mechanics (the actual recipe): Level 0 specific function → functional intent Level 1 must satisfy → specialized/zoomed into Level 1 functional architecture (operands, processes); Level 0 form separately decomposed into Level 1 form, mapped onto those processes (the zigzag: function → form → function)
  • Rest of Level 1 (non-idealities, supporting processes/form, interfaces) follows using the same Ch.6 machinery
  • → Connect back to the opening: function-goal reasoning is why concept→Level 1→Level 2 can be applied recursively — same pattern reapplies one level lower each time

  • Zigzagging alternates function and form — form questions (4a–4f) and function-to-form mapping (6a–6g) round out the picture
  • Function-goal reasoning governs the whole process: the specific function at one level is the functional intent one level down

8.3 Developing the Level 2 Architecture

Intent and Recursion at Level 2

  • The complete Level 1 architecture already has 18+ internal processes (9 value-related + supporting) plus their form and interfaces — already a great deal of complexity
  • The key question: is Level 1 the right decomposition — or at least a good one? We can’t fully judge that without seeing how the details actually work
  • We recursively apply Table 8.1, one more level down: each function at Level 1 becomes a statement of functional intent at Level 2 — the same function–goal reasoning as Figure 8.3, one level lower

Tip

Example: “purchasing tickets” (Level 1) becomes the Level 2 intent, specialized down to purchasing online and beyond.

  • Open Section 8.3 honestly about scale: a complete Level 1 architecture (from Fig 8.2) already has ≥18 internal processes (9 value-related + ≥9 supporting), plus form and interfaces — already a lot for “Level 1”
  • Motivating question: is this actually the right decomposition — or at least a good one? Honestly, we can’t judge yet
  • Book’s answer (major theme again in Ch.13): the real info about how entities should cluster/modularize at Level 1 is hidden at Level 2 — need to dive down first
  • Mechanism: recursively apply Table 8.1, one level deeper — each Level 1 function becomes Level 2 functional intent (same pattern as Figure 8.3, shifted down)
  • → Worked example for the rest of the section: “purchasing tickets” (Level 1 function) becomes the Level 2 intent, specializes to purchasing online, zoomed further from there

Do We Need Level 3?

  • Together, Tables 8.2 and 8.3 are the Level 2 architecture — though still without supporting systems, interfaces, or external accompanying systems
  • Typical scale: Level 1 ≈ 20–30 entities; Level 2 ≈ 50–100; Level 3 would run into the hundreds

Three levels are hard to develop and too much to comprehend easily — we usually don’t need to go to Level 3. Examining Level 2 exists to confirm Level 1’s abstractions and inform modularization — not to fully re-architect everything one level deeper.

  • Be honest, as the book is: Tables 8.2/8.3 together are the Level 2 architecture — but still without supporting systems, interfaces, or external accompanying systems (same gaps as the initial Level 1 picture)
  • Not sloppiness — deliberate scoping to focus on core value-related structure
  • Scale rules of thumb: Level 1 ≈ 20–30 entities (recalls Ch.3’s 7±2 per level, compounding), Level 2 ≈ 50–100, Level 3 would run into the hundreds — echoes Ch.3’s simple/medium/complex arithmetic, roughly geometric compounding
  • → Practical conclusion: three levels are hard to develop and too much to comprehend at once — usually don’t need Level 3. Level 2’s purpose: confirm Level 1’s abstractions, inform modularization (Section 8.5) — not re-architect one level deeper than necessary

Section 8.3 Summary

  • Level 2 architecture is developed by recursively applying the same procedure: each Level 1 function becomes the Level 2 functional intent
  • The result is dramatically more detailed — dozens of processes and operands, mapped onto dozens of form instruments
  • The purpose isn’t more detail for its own sake: it’s to validate the Level 1 decomposition and enable good modularization (Section 8.5)
  • Second checkpoint of the chapter — students should explain in their own words how Level 2 gets built: recursively re-applying Table 8.1, each Level 1 function as functional intent one level down (function-goal reasoning again, as previewed in Fig 8.3)
  • Result on air transportation: 18 → 28 processes (22 form instruments) — a dramatic increase in detail
  • Emphasize hardest: the point isn’t detail for its own sake — it validates whether Level 1 was a good decomposition, and sets up modularization (Section 8.5’s payoff)
  • → Before that: Section 8.4 detours to repeat the process on a different system (home data network) to show the method isn’t specific to air travel

8.4 Home Data Network Architecture at Level 2

A Second Worked Example

  • Recall from Chapter 7: solution-neutral function is buying a book; the integrated concept is accessing the Internet via a DSL modem, residential gateway/switch, WiFi access point, and laptop
  • Figure 8.5 traces an IP packet’s Level 2 architecture, from the laptop until it leaves the house — broken into three layers: Internet, Link, and Physical (mirroring the bottom of the standard Internet protocol suite)

Tip

Layering lets a network designer view the system through the lens of a single layer at a time — powerful for scalability and robustness, but it makes the functional pathway of the data harder to trace end to end.

  • Section purpose: not new theory — demonstrate the air-transportation method generalizes to a genuinely different system, the home data network
  • Recall Ch.7 setup: solution-neutral function = “buying a book” (mundane stand-in for “using the Internet at home”); integrated concept = accessing the Internet via DSL modem, residential gateway/switch, WiFi access point, laptop
  • Figure 8.5 traces an IP packet’s journey at Level 2 detail, laptop → leaving the house toward the ISP — not a business-process pathway like the airline
  • Layering: Internet, Link, Physical — mirrors the bottom three layers of the standard Internet protocol suite (application/transport layers omitted, minor role within the home network)
  • Layering trade-off (fragment): lets a designer reason about one layer at a time (same “abstraction” idea as Ch.2) — gives scalability, robustness, flexibility
  • → But makes it harder to trace the data’s continuous end-to-end functional pathway — exactly the harder, “linearized” view the next two figures walk through anyway, because it’s valuable despite cutting against how networks are normally discussed

Figure 8.5a · Laptop to Wireless Access Point

The laptop creates an IP packet, encapsulates it into an 802.11 frame with MAC addressing (via ARP), and broadcasts it over WiFi; the WAP receives, de-encapsulates, and re-encapsulates it as an Ethernet frame toward the switch. Source: Crawley, Cameron & Selva (2016), Fig. 8.5.

  • First leg of the packet’s journey — walk sequentially, the process-tracing the last slide flagged as valuable
  • Internet layer: laptop creates an IP packet — source IP (laptop), destination IP (e.g. a server), data payload
  • Link layer: packet encapsulated into an 802.11 (WiFi) frame, adds MAC addressing
    • MAC ≠ IP: MAC = local-area “neighborhood” location, no internet-wide routing
    • Source MAC = static property of the NIC; destination MAC = looked up via ARP table (maps destination IP → destination MAC on the local network)
  • Physical layer: laptop’s antenna modulates bits onto a 2.4-GHz signal, broadcasts
  • → WAP receives, de-encapsulates back to IP packet, reads destination, determines it must go through the residential gateway, re-encapsulates as a new Ethernet frame addressed to the gateway — next leg on the following slide

Figure 8.5b · Switch to the ISP

The switch error-checks, reads the destination, and forwards the frame to the gateway, which de-encapsulates it, performs NAT (network address translation) to swap the private IP for a public one, and re-encapsulates it as PPPoE — modulated by the DSL modem onto the phone line toward the ISP. Source: Crawley, Cameron & Selva (2016), Fig. 8.5.

  • Second and final leg inside the house
  • Ethernet frame → Physical layer → bits over copper cable to the switch
  • Switch buffers, reads destination MAC to forward, error-checks the transfer, writes back out toward the gateway
  • Gateway: de-encapsulates to the IP packet, performs NAT (network address translation) — swaps laptop’s private IP for the gateway’s public IP
  • → NAT’s two benefits: conserves scarce public IP addresses, and adds security (devices never directly broadcast their address to the Internet)
  • Re-encapsulated into a PPPoE frame (residential gateway ↔︎ ISP protocol), modulated by the DSL modem onto the phone line → telephone exchange → ISP
  • → Complete journey across three layers and two figures — a concrete demonstration of Level 2 detail on a system entirely different from air transportation

8.5 Modularizing the System at Level 1

Why Modularize?

  • We initially organized Level 1 by the timeline of air travel: ticketing, checking in, loading, transporting, unloading, checking out. Is that actually a good decomposition?
  • Objective: cluster entities that are tightly interconnected — this minimizes interactions across modules and maximizes coherence within them
  • First choice: cluster by process (via shared operands) or by form (via structure) — Box 8.1 covers both
  • Return to the motivating question from the start of Section 8.3 — now finally answerable
  • Original Level 1 decomposition organized by the timeline (ticketing, checking in, loading, transporting, unloading, checking out) — natural, but is it actually good (in the rigorous sense from Ch.3’s decomposition/hierarchy discussion)?
  • Level 2 detail finally lets us ask this properly
  • Clustering objective: cluster tightly interconnected entities, minimizing cross-module interactions, maximizing within-module coherence — echoes Ch.3’s modular-vs-integral spectrum
  • First choice point (Box 8.1, next): cluster by process (shared operands) or by form (structural/spatial relationships)
  • → Rest of this section works the process-based route on air transportation; form-based route is an equally legitimate alternative, not covered in full

Box 8.1 · Clustering by Interactions

Three tasks: choose the basis for clustering (processes or form), represent that information (as a DSM), and compute the clusters. Replacing the interaction type (create/affect/instrument) with a simple count of connections lets a clustering algorithm rearrange rows and columns into tightly coupled blocks.

Tip

Here, clustering is based on processes, linked through shared operands: two processes that touch many of the same operands are assumed to be tightly coupled.

  • Unpack the three-step procedure the rest of Section 8.5 executes:
    1. choose the clustering basis — process or form
    2. represent it as a DSM (design structure matrix / N-squared table, from Ch.2 — same tool as the amplifier circuit’s relationship tables)
    3. compute the clusters via a systematic algorithm, not eyeballing it
  • Key simplification: earlier chapters preserved interaction type (I/a/c notation from Table 8.2); for clustering, that’s suppressed to a simple count — is there a connection, and how many shared ones
  • → Trade-off: loses type info, but lets a mechanical algorithm rearrange rows/columns into contiguous tightly-coupled blocks — much harder to automate otherwise
  • Choice for the worked example (fragment): cluster by process, coupling = shared operands. Sets up Table 8.4’s DSM next

Table 8.4 · DSM Clustering of Level 2 Processes

The Thebeau algorithm reorders the 28×28 process-interaction matrix so tightly-coupled entities fall into contiguous, shaded blocks along the diagonal — six clusters emerge. Individual cell values aren’t the point here; the block-diagonal pattern is. Source: Crawley, Cameron & Selva (2016), Table 8.4.

  • How to read this table — individual cell values aren’t the point, the pattern is
  • 28×28 matrix (all 28 Level 2 processes), each cell = count of shared operands between row and column process
  • Thebeau algorithm (Ronnie Thebeau’s 2001 MIT master’s thesis on system-interface knowledge management): reorders rows/columns so highly-coupled entities sit next to each other
  • Payoff: shaded block-diagonal pattern, six clusters emerge — groups that interact heavily internally, little across
  • → What matters is the shape of the reordered pattern (clean block-diagonal vs. messy), not individual numbers. Same technique (DSM + clustering) returns in much more depth in Chapter 13 — get comfortable reading it now

Six Clusters Emerge

  • Cluster 1 (reservation): linking, learning, reserving, purchasing, amending
  • Cluster 2 (ticket): changing, issuing, crediting
  • Clusters 3–5 (passenger, checked bags, carry-on bags): each follows the same check-in → move → check-out pattern for its respective operand
  • Cluster 6 (secondary experience): alerting, informing, entertaining, nourishing

Tip

This clustering is organized by operand path, not by chronology — a genuinely different decomposition than the original timeline-based one.

  • Name the six blocks in human-readable terms — where the abstract clustering turns into architectural insight
  • Cluster 1 (reservation): linking, learning, reserving, purchasing, amending
  • Cluster 2 (ticket): changing, issuing, crediting
  • Clusters 3–5: passenger, checked bags, carry-on bags — strikingly similar structure, each following check-in → move → check-out
  • Cluster 6 (secondary experience): alerting, informing, entertaining, nourishing
  • → Fragment’s payoff, answers the section’s opening question: organized around operand path, not chronology (the original Level 1 timeline). Two different lenses on the same system, genuinely different groupings — neither obviously “the” right one

Two Decompositions, Neither “Right”

  • The clustering isn’t perfect — interactions still cross block boundaries — and clustering doesn’t guarantee a better modularization, just a systematic one
  • The original, timeline-based decomposition (Figure 8.2) and this operand-based one (Table 8.4) represent two different ways of organizing the same system

If the airline cared about running time, the time-based organization might make more sense. If it cared about end-to-end reliability per passenger or bag, the operand-based clustering looks more appropriate.

  • Push back deliberately against treating the algorithmic clustering as automatically superior — a lesson about the limits of algorithmic methods
  • The clustering isn’t perfect even on its own terms: meaningful interactions still cross block boundaries
  • More fundamentally: a clustering algorithm doesn’t guarantee a better modularization, only a systematic, reproducible one
  • Central conclusion: timeline-based (Fig 8.2) and operand-based (Table 8.4) decompositions are just two ways of organizing the same system — neither objectively “right”
  • → Resolve via what the architect optimizes for: running time favors the time-based organization; end-to-end reliability per passenger/bag favors the operand-based clustering
  • Generalizable lesson: modularization isn’t purely mechanical — it’s anchored to the system’s actual goals, echoing Chapter 2’s focus principle (“which entities matter” depends on the question)

Section 8.5 Summary

  • Modularizing Level 1 well requires expanding to Level 2, examining relationships by process or form, and then clustering
  • Clustering algorithms maximize local interaction and minimize cross-block interaction — better informing internal interfaces and how design work gets distributed
  • No single decomposition is universally “correct” — the right one depends on what the architect is optimizing for
  • Section checkpoint before the chapter wrap-up — students should walk through the full recipe: expand to Level 2 (8.3), examine relationships via process or form (Box 8.1), represent as a DSM, apply a clustering algorithm (Thebeau) to surface tightly-coupled blocks
  • What this buys practically: informs where internal interfaces should sit, and how design work can be distributed across teams/suppliers — loosely-coupled modules need far less cross-team coordination
  • → Central caution, worth carrying forward: no decomposition is universally “correct” — the right one depends on what the architect is optimizing for. Not a limitation of the method — a fundamental feature of architectural decision-making, revisited especially in Part 3
