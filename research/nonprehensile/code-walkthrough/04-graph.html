4. The contact graph

catalog/graph.py builds edges between templates: transfer-adjacent (same body pair, and the features are adjacent on both bodies, so one contact can slide into the other) and shared-feature (the two templates use a common feature). It should also carry the exclusion table. This step counts the edges and looks at what is actually stored.

Two graphs, not one. The paper uses two graphs, and it helps to keep them apart from here on.

  • The contact graph G, built on this page: its vertices are templates, with typed edges between them. It is fixed by the scene.
  • The marking graph W: its vertices are markings (formations, the bit vectors of step 3), and its edges are edits (make, break, and the transfer of Decision 1). The planner searches W. In the code, Cand (step 6) generates W’s edges out of a node and Search (step 8) walks them; W is never stored, only expanded as the search goes.

G feeds W: exclusion edges decide which markings are valid (W’s vertices), and transfer-adjacent edges decide which transfers exist (W’s transfer edges, Decision 1: transfer(c → d) requires c and d to be transfer-adjacent). Shared-feature edges do not shape W; the paper uses them, with the transfer edges, as the network’s message-passing structure.

python walkthrough/04_graph.py
The script, 04_graph.py (download) 
"""Step 4: the contact graph (catalog-level edges).

ContactGraph builds two edge types over templates: transfer-adjacent (same
body pair, features adjacent on both bodies) and shared-feature (the two
templates share a feature). Count them, and look at what the edge list
actually stores.
"""
from collections import Counter

from cmg.catalog.graph import ContactGraph, EdgeTypes

from _common import STEP_YAML, load_spec, template_names

graph = ContactGraph.from_yaml(str(STEP_YAML))
catalog = graph.catalog
names = template_names(load_spec(), catalog)

print("Edges by type:", dict(Counter(EdgeTypes(t).name for _, _, t in graph.edges)))
print("First three stored edges:", graph.edges[:3])
print("Has an excluded-edge list:", hasattr(graph, "edges_excluded"))

# Recompute with catalog positions so the edges can be read.
index = {id(t): i for i, t in enumerate(catalog)}
first = names.index("B:zn-L:boundary")
print(f"\nNeighbours of {names[first]} (template {first}):")
for t1, t2 in ((a, b) for a in catalog for b in catalog if a is not b):
    if index[id(t1)] != first:
        continue
    kinds = []
    if catalog.transfer_adjacent(t1, t2):
        kinds.append("transfer-adjacent")
    if set(t1.key()) & set(t2.key()):
        kinds.append("shared-feature")
    if kinds:
        print(f"  {names[index[id(t2)]]:18s} {', '.join(kinds)}")

What to notice

  • Every stored edge is (None, None, type). Edges are recorded by template_id, which Catalog.from_spec never sets (step 2). The edge list cannot be mapped back to templates. The script works around this by recomputing the edges with catalog positions.
  • The exclusion table is dropped. ContactGraph.from_spec passes edges_excluded, but __init__ never stores it.
  • Nothing downstream reads this ContactGraph object. The search does walk a graph, the marking graph W, but Cand (step 6) builds W’s edges from the catalog and the bit vectors alone, with make and break only. So no exclusion is enforced anywhere today, and transfer edits do not exist yet (they arrive in step 2 of the critical path).
  • Adjacency follows the box’s faces. B:zn-L is transfer-adjacent to the four side faces on the floor, not to B:zp-L: opposite faces share no edge.
  • Shared-feature edges here include shared environment features. B:zn-L and B:xp-L share only the floor’s boundary, yet they are linked.
  • Each edge appears twice, once in each direction.

Both defects (unset IDs, dropped exclusions) are on the list of code issues for Angelo in the discussion compendium.

Code to read

  • src/cmg/catalog/graph.py: ContactGraph.__init__ and __create_default_edges.
  • src/cmg/catalog/templates.py, Catalog.transfer_adjacent, and src/cmg/geometry/features.py, the adjacent method of BoxFaceFeature and BoxVertexFeature.

Exercises

4.1 Account for the 96 transfer-adjacent edges.

TipSolution

Within one body pair, the other body’s feature is a single boundary, which is adjacent to itself, so two templates are transfer-adjacent exactly when their box faces are adjacent. Each face is adjacent to the four faces on other axes, giving 6 × 4 = 24 ordered pairs per body pair. With four body pairs that makes 4 × 24 = 96.

4.2 Account for the 192 shared-feature edges. How many would there be if only shared object features counted, as the docstring’s name (shared-object-feature) suggests?

TipSolution

Take a template (box face f, other feature b). It shares f with the three other templates that use f (one per other body pair), and b with the five other templates of its own pair. That gives 8 neighbors per template and 24 × 8 = 192 ordered edges. Counting only the shared box face leaves 3 per template, 24 × 3 = 72.

4.3 Fix the missing template IDs so that the stored edges name templates, and check that the test suite still passes.

TipSolution

In src/cmg/catalog/templates.py, Catalog.from_spec, re-create the templates with their positions just before the ExecutionWorld line:

        templates = [
            Template.create(t.feature1, t.feature2, template_id=i)
            for i, t in enumerate(templates)
        ]
        exec_world = ExecutionWorld(spec.execution)
